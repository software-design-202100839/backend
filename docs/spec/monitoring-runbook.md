# SSCM 모니터링 운영 가이드 (Runbook)

Grafana 대시보드의 각 패널이 **어떤 상황에서 어떻게 움직이고, 그때 뭘 해야 하는지** 정리한 문서.

## 시스템 규모 가정

SSCM은 **다중 학교 SaaS 확장을 전제로 설계**된 시스템.

| 단계 | 규모 | 동시 사용자 |
|------|------|-----------|
| MVP (현재) | 1개 학교, 교사 30명 | ~30명 |
| 확장 Phase 1 | 10개 학교 | ~200~500명 |
| 확장 Phase 2 | 교육청/지역 단위 | ~1000+명 |

이 문서의 임계값과 대응 방법은 **Phase 1~2 규모**를 기준으로 작성.
Kafka, OLAP 분리, Redis 캐시, ECS Auto Scaling은 이 규모에서 필수적.

## 1계층: 앱 메트릭 (Prometheus → Spring Actuator)

### 1-1. Uptime

| 항목 | 내용 |
|------|------|
| **정상** | 값이 계속 증가 (예: 10.7 hours) |
| **이상** | 갑자기 0으로 리셋 |
| **의미** | 앱이 재시작됨 — OOM, 배포, 크래시 |
| **대응** | CloudWatch ECS 로그 확인 → OOM이면 메모리 증가, 크래시면 최근 커밋 롤백 |

### 1-2. CPU Usage

| 항목 | 내용 |
|------|------|
| **정상** | 0.5~5% (트래픽 없을 때), 요청 시 일시적 상승 |
| **이상** | 지속적 50%+ |
| **그래프** | 평소 바닥 → 부하 시 스파이크 → 다시 바닥 (정상). 일직선으로 높으면 이상 |
| **의미** | 무한 루프, 과도한 GC, 비효율 쿼리 |
| **대응** | Thread dump 확인 (`/actuator/threaddump`), 느린 쿼리 추적 |

### 1-3. HTTP 5xx Errors (1m)

| 항목 | 내용 |
|------|------|
| **정상** | 0 (초록 배경) |
| **이상** | 1 이상 (빨간 배경) |
| **그래프** | 0에서 갑자기 숫자 올라감 |
| **의미** | 서버 내부 에러 — NullPointerException, DB 연결 실패 등 |
| **대응** | ① ECS 로그에서 에러 스택트레이스 확인 ② 배포 직후면 롤백 검토 ③ DB 연결이면 HikariCP 패널 같이 확인 |
| **알림** | 5xx > 0 → 즉시 이메일 발송 (critical) |

### 1-4. JVM Heap Memory

| 항목 | 내용 |
|------|------|
| **정상** | **톱니바퀴 패턴** — Used가 올라갔다 GC에 의해 떨어지고 반복 |
| **이상** | Used가 Max에 점점 접근하며 안 떨어짐 (일직선 상승) |
| **그래프 예시** | `정상: /\/\/\/\` vs `이상: /‾‾‾‾` |
| **의미** | 메모리 누수 — 객체가 GC되지 않고 쌓임 |
| **대응** | ① heap dump 생성 (`jmap -dump`) ② 최근 코드 변경에서 컬렉션/캐시 누수 확인 ③ 임시: JVM heap 크기 증가 |
| **알림** | Used/Max > 90% 2분 지속 → 이메일 발송 (warning) |

### 1-5. HTTP Request Rate

| 항목 | 내용 |
|------|------|
| **정상** | 엔드포인트별로 일정한 패턴. `/actuator/health`와 `/actuator/prometheus`는 15초마다 일정 |
| **이상** | 특정 엔드포인트에 갑자기 과도한 요청 |
| **의미** | 정상 트래픽 증가 또는 DDoS/크롤러 공격 |
| **대응** | ① 특정 IP의 공격이면 WAF/Security Group 차단 ② 정상 트래픽이면 ECS 스케일 아웃 |

### 1-6. HTTP Response Time (p95)

| 항목 | 내용 |
|------|------|
| **정상** | 대부분 50ms 이하. `/api/v1/analytics/chat`은 AI 호출이라 200ms+ 가능 |
| **이상** | p95가 1초 초과 |
| **그래프** | 평소 바닥 → 특정 시점부터 스파이크가 높아짐 |
| **의미** | 느린 DB 쿼리, 외부 API 타임아웃, GC 지연 |
| **대응** | ① 어떤 엔드포인트가 느린지 확인 (그래프 범례) ② DB 쿼리면 RDS CPU 패널 같이 확인 ③ GC면 GC Pause Time 패널 확인 |
| **알림** | p95 > 1초 2분 지속 → 이메일 발송 (warning) |

### 1-7. HikariCP Connection Pool

| 항목 | 내용 |
|------|------|
| **정상** | Active 낮음 (1~3), Idle 나머지, Max=20, Pending=0 |
| **이상** | Active가 Max(20)에 근접, Pending > 0 |
| **그래프** | Active(초록)가 Max(파랑) 라인에 붙고, Pending(빨강)이 0에서 올라감 |
| **의미** | 느린 쿼리가 커넥션을 오래 잡고 있음 → 다른 요청이 대기 |
| **대응** | ① RDS CPU 확인 — DB가 병목인지 ② 느린 쿼리 최적화 (인덱스) ③ 임시: `maximum-pool-size` 증가 (부작용: DB 부하 증가) |
| **알림** | Pending > 0 1분 지속 → 이메일 발송 (warning) |

### 1-8. GC Pause Time

| 항목 | 내용 |
|------|------|
| **정상** | minor GC: 수 μs~ms, major GC: 가끔 발생 |
| **이상** | major GC가 빈번하게 발생하거나, pause time이 200ms+ |
| **의미** | heap이 부족해서 GC가 자주 돌아감 → 앱 전체가 멈추는 시간 증가 |
| **대응** | ① JVM Heap 패널과 같이 확인 ② heap 크기 증가 ③ 메모리 누수 여부 점검 |

## 2계층: 비즈니스 메트릭 (Prometheus → Micrometer Counter)

### 2-1. 로그인 성공/실패 비율

| 항목 | 내용 |
|------|------|
| **정상** | 성공(초록) 위주, 실패(빨강) 거의 없음 |
| **이상 1** | 실패가 성공보다 많아짐 (빨강이 초록 위를 덮음) |
| **이상 2** | 성공/실패 둘 다 0 (아무도 로그인 안 함) |
| **의미 1** | 브루트포스 공격 또는 인증 장애 (DB 연결 실패, JWT 시크릿 불일치) |
| **의미 2** | 프론트엔드 장애 또는 DNS 문제 |
| **대응 1** | ① ECS 로그에서 실패 원인 확인 ② 특정 IP 반복이면 차단 ③ 배포 직후면 JWT_SECRET 환경변수 확인 |
| **알림** | 실패율 > 50% 2분 지속 → 이메일 발송 (warning) |

### 2-2. 도메인 데이터 등록 추이 (성적/피드백/상담)

| 항목 | 내용 |
|------|------|
| **정상** | 학기 중: 성적 등록이 주기적으로 발생. 방학 중: 거의 0 |
| **이상** | 학기 중인데 모든 도메인이 0 |
| **의미** | 기능 장애 — 5xx 에러는 없지만 비즈니스 기능이 안 되는 "침묵의 장애" |
| **대응** | ① 5xx 패널이 0인데 여기가 0이면 → 프론트엔드 문제 가능성 ② CORS, API URL 확인 ③ 직접 API 호출해서 테스트 |

### 2-3. Kafka 이벤트 발행 속도

| 항목 | 내용 |
|------|------|
| **정상** | 도메인 등록 추이와 비슷한 패턴으로 움직임 |
| **이상** | 도메인 등록은 되는데 Kafka 이벤트가 0 |
| **의미** | 이벤트 발행 로직 장애 — OLAP 파이프라인이 끊김 |
| **대응** | ① Kafka 브로커 상태 확인 (MSK 콘솔) ② `AnalyticsEventBridge` 로그 확인 ③ Kafka 연결 설정 확인 |

### 2-4. Kafka Consumer Lag

| 항목 | 내용 |
|------|------|
| **정상** | lag ≈ 0 (소비가 생산을 따라잡음) |
| **이상** | lag이 계속 증가 (우상향) |
| **그래프** | 0 근처에서 평평해야 정상. 우상향이면 소비자가 밀리고 있음 |
| **의미** | Consumer 처리 속도 < Producer 발행 속도. 집계 쿼리가 느리거나 Consumer가 죽음 |
| **대응** | ① Consumer 로그 확인 — 에러 발생 여부 ② Analytics DB 쿼리 최적화 ③ Consumer 파티션 수 증가 검토 |

### 2-5. Redis 캐시 히트율

| 항목 | 내용 |
|------|------|
| **정상** | 80%+ (대부분 Redis에서 해결) |
| **이상** | 50% 이하로 떨어짐 |
| **그래프** | 100% 근처에서 평평 → 갑자기 뚝 떨어지면 이상 |
| **의미** | ① Redis 장애로 전부 DB fallback ② TTL이 너무 짧아서 miss 빈발 ③ 새로운 토큰이 대량 발급됨 (캐시에 없는 키) |
| **대응** | ① ElastiCache 콘솔에서 Redis 상태 확인 ② Redis 연결 에러 로그 확인 ③ TTL 조정 검토 |

## 3계층: 인프라 메트릭 (CloudWatch)

### 3-1. ECS CPU / Memory 사용률

| 항목 | 내용 |
|------|------|
| **정상** | CPU 1~5%, Memory 40~50% |
| **이상 - 과부하** | CPU 80%+ 또는 Memory 90%+ 지속 |
| **이상 - 낭비** | CPU 항상 1% 미만, Memory 20% 미만 |
| **그래프** | CPU는 요청에 따라 스파이크, Memory는 완만한 변화. CPU가 계단식으로 올라가면 leak 의심 |
| **대응 - 과부하** | ① ECS 태스크 수 증가 (Auto Scaling) ② 태스크 스펙 업 (vCPU/Memory) |
| **대응 - 낭비** | 스펙 다운으로 비용 절약. 현재 0.5 vCPU/1GB → 과도하면 0.25 vCPU/0.5GB |
| **현재 수치** | CPU ~1%, Memory ~45% → **정상, Memory 여유 있음** |

### 3-2. RDS CPU 사용률

| 항목 | 내용 |
|------|------|
| **정상** | 3~10% (db.t3.micro 기준) |
| **이상** | 70%+ 지속 |
| **그래프** | 평소 3~5% → 느린 쿼리 실행 시 스파이크 → 부하 테스트 시 60~80% |
| **의미** | 인덱스 없는 풀 스캔, N+1 쿼리, 동시 접속 급증 |
| **대응** | ① `EXPLAIN ANALYZE`로 느린 쿼리 식별 ② 인덱스 추가 ③ 읽기 부하면 Read Replica 검토 ④ 인스턴스 업그레이드 (db.t3.small) |
| **현재 수치** | sscm-db: 3.7%, analytics-db: 3.5% → **정상** |

### 3-3. RDS DB 커넥션 수

| 항목 | 내용 |
|------|------|
| **정상** | sscm-db: ~20 (HikariCP max=20), analytics-db: ~10 |
| **이상** | max_connections 한계(db.t3.micro: ~60)에 근접 |
| **그래프** | 평평한 직선이 정상. 계단식 증가면 커넥션 누수 |
| **의미** | HikariCP가 max까지 점유, 또는 외부 클라이언트가 직접 접속 |
| **대응** | ① HikariCP 패널과 대조 — Active가 높으면 쿼리 병목 ② 커넥션 누수 확인 (트랜잭션 미종료) ③ DB 인스턴스 업그레이드 |
| **현재 수치** | sscm-db: 20, analytics-db: 10 → **정상 (풀 사이즈만큼 사용)** |

### 3-4. ALB 요청 수 / 5xx

| 항목 | 내용 |
|------|------|
| **정상** | 요청 수: 트래픽에 비례. 5xx: 0 |
| **이상 1** | 요청 수가 갑자기 0 |
| **이상 2** | 5xx가 급증 |
| **그래프** | 요청 수(초록) 위에 5xx(노랑)가 겹침. 5xx가 보이면 문제 |
| **의미 1** | DNS 문제, ALB 자체 장애, 모든 Target unhealthy |
| **의미 2** | ECS 앱에서 에러 발생. **ELB 5xx vs Target 5xx 구분 중요** — ELB 5xx는 인프라 문제, Target 5xx는 앱 문제 |
| **대응** | ① Target 5xx → ECS 로그 확인 ② ELB 5xx → Target Group 헬스체크 확인 ③ 요청 0이면 → Route 53/CloudFront 확인 |
| **현재 수치** | 5분당 20~150건, 5xx ≈ 0 → **정상** |

## 장애 추적 흐름 (Top-Down)

사용자가 "안 돼요"라고 신고하면, **위에서 아래로** 따라갑니다:

```
1. 비즈니스 메트릭 — 문제가 "있는지" 확인
   └─ 성적 등록이 0인가? 로그인 실패율이 높은가?

2. 앱 메트릭 — 문제의 "증상" 확인
   └─ 5xx가 나오나? p95가 느린가? 커넥션 풀이 찼나?

3. 인프라 메트릭 — 문제의 "원인" 확인
   └─ RDS CPU가 100%인가? ECS 메모리가 찼나? ALB가 죽었나?
```

### 예시 시나리오

**"A학교 교사들이 성적 등록이 안 된다고 신고"**
```
① 도메인 등록 추이 → 성적 0건 확인 (문제 존재)
② HTTP 5xx → 5xx 급증 확인 (앱 에러)
③ HikariCP → Pending > 0 (커넥션 대기)
④ RDS CPU → 95% (DB 병목!)
→ 결론: 여러 학교의 시험 기간이 겹치면서 분석 쿼리와 운영 트랜잭션이 경합
→ 대응: OLAP DB 분리가 이 문제를 방지. 운영 DB에서 분석 쿼리 제거 확인
```

**"여러 학교에서 동시에 페이지가 느리다고 신고"**
```
① 비즈니스 메트릭 → 정상 (데이터는 들어오고 있음)
② HTTP p95 → 2초 (느림!)
③ ECS CPU → 85% (인스턴스 과부하)
④ Auto Scaling → 태스크 1개에서 아직 스케일 아웃 안 됨
→ 결론: 트래픽 급증에 스케일 아웃이 안 따라감
→ 대응: Auto Scaling CPU threshold 확인 (70%) + 태스크 증가 확인
```

**"특정 학교에서 로그인 실패가 대량 발생"**
```
① 로그인 성공/실패 → 실패율 90%
② HTTP 5xx → 0 (서버 에러 아님, 401이 나오고 있음)
③ Redis 히트율 → 정상
→ 결론: 브루트포스 공격 또는 해당 학교 비밀번호 일괄 만료

```

**"분석 대시보드 데이터가 실시간 반영 안 됨"**
```
① 도메인 등록 추이 → 성적 등록은 정상
② Kafka 이벤트 발행 → 정상 발행 중
③ Kafka Consumer Lag → lag 계속 증가 (우상향!)
→ 결론: 10개 학교가 동시에 데이터 입력하면서 Consumer 처리량 초과
→ 대응: Consumer 파티션 수 증가 또는 Consumer 인스턴스 추가
```
