## 분석

### Before → 최종 개선
- p95: 906ms → **791ms (13% 개선)**
- 처리량: 133 → **140 req/s (5% 향상)**
- 최대 응답: 2,614ms → **1,900ms (27% 개선)**

### 왜 After (데이터 없음)가 가장 느렸나
- 새 배포 직후 JVM 웜업 미완료
- Redis 연결 초기화 오버헤드
- 분석 DB에 데이터 없어서 404 반환 경로가 오히려 느림 (예외 생성 비용)

### 진짜 병목: Analytics DB 쿼리
```
API 요청 흐름:
1. ALB 라우팅              ~1ms
2. JWT 블랙리스트 체크      ~2-5ms → Redis로 <1ms (개선됨)
3. Analytics DB 쿼리       ~300ms ← 지배적
4. DTO 변환 + 응답         ~1ms
```

JWT 캐시로 2-5ms를 줄여도 전체 ~300ms 대비 미미. **DB 쿼리가 지배적 병목**.

### http_req_failed 49.99% 설명
- k6 스크립트가 학생 ID=1로 조회하는데, 일부 분석 API는 404 반환
- 404는 서버 에러가 아님 (checks는 100% 통과)
- 5xx 에러는 0%

## Redis 도입의 의미

### 현재 규모 (200 VU)에서
- JWT 캐시 단독으로는 체감 개선 미미
- 하지만 데이터 + JVM 워밍업 후 전체적으로 13% 개선 관찰

### 대규모 (1000+ VU)에서 Redis가 의미 있는 이유
1. **커넥션 풀 고갈 방지**: 매 요청 DB SELECT 1회 제거 → 커넥션 여유 확보
2. **응답시간 안정성**: DB 부하 증가 시 블랙리스트 체크 시간 급등 방지
3. **다중 인스턴스 대응**: ECS Task 여러 대에서 동일한 블랙리스트 상태 공유

### 발표 답변
> "200 VU 테스트에서 Redis 캐시 도입 후 p95가 906ms → 791ms로 13% 개선되었습니다.
> 현재 병목은 분석 DB 쿼리(~300ms)로, Redis 캐시의 효과는 제한적입니다.
> Redis 도입은 현재 성능 개선보다 **확장성 확보** 목적입니다.
> 동시 접속자 1000+ 수준에서 커넥션 풀 고갈 방지에 핵심 역할을 합니다."

## 후속 과제: 병목 개선 방안

| 방안 | 효과 | 복잡도 | 비용 |
|------|------|--------|------|
| 분석 DB 인덱스 최적화 | 쿼리 시간 감소 | 낮음 | 무료 |
| RDS 스펙 업 (db.t3.small) | I/O 성능 향상 | 낮음 | +$0.02/hr |
| 분석 API 응답 캐시 (Redis) | 반복 조회 제거 | 중간 | 무료 (기존 Redis 사용) |
| Read Replica 추가 | 읽기 부하 분산 | 중간 | +$0.02/hr |
| ECS Task 스펙 업 (1 vCPU) | CPU 병목 해소 | 낮음 | +$0.03/hr |
