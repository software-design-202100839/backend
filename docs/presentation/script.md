# SSCM 발표 대본 (10분)

---

## 슬라이드 1: 소개 (1분)

> 안녕하세요, 이승희입니다. 저는 SSCM, Smart School Class Management라는 학생 성적 및 상담 관리 시스템을 개발했습니다.
>
> 현재 학교 현장에서는 성적 입력, 피드백 작성, 상담 기록, 학생부 관리가 각각 다른 시스템에 흩어져 있고, 교사가 학생 한 명의 전체 학습 현황을 파악하려면 여러 화면을 오가야 합니다.
>
> SSCM은 이 모든 교육 데이터를 하나의 시스템에서 관리하고, **실시간 분석 대시보드와 AI 어시스턴트**로 교사가 데이터 기반 의사결정을 할 수 있도록 지원합니다.
>
> 기술 스택은 Spring Boot 3.5, React 19, PostgreSQL 16이고, AWS 위에 프로덕션 배포되어 있습니다.

## 슬라이드 2: 핵심 기능 (1분)

> SSCM의 핵심 기능은 크게 4가지입니다.
>
> 첫째, **교육 데이터 관리** — 성적, 학생부, 피드백, 상담내역을 CRUD로 관리합니다. 역할별 접근 제어가 있어서 교사, 학생, 학부모가 각각 다른 데이터를 봅니다.
>
> 둘째, **OLAP 분석 파이프라인** — 운영 DB의 변경 이벤트를 Kafka로 발행하고, Consumer가 분석 DB에 집계합니다. 운영과 분석이 물리적으로 분리되어 있어서 분석 쿼리가 성적 입력 API에 영향을 주지 않습니다.
>
> 셋째, **교육 업무 AI** — 단순 조회 챗봇이 아닙니다. Function Calling으로 정형 데이터를 조회하고, RAG + pgvector로 피드백·상담 텍스트를 의미 검색하고, 학기말 종합 의견 초안을 생성합니다. 교사가 수정한 뒤 저장하는 Human-in-the-Loop 구조이고, 근거 기록을 함께 표시합니다. 또한 Kafka 이벤트로 위험 학생을 감지해서 교사에게 먼저 알려주는 Proactive 알림 봇도 있습니다.
>
> 넷째, **다중 학교 멀티테넌시** — School 엔티티와 JWT의 schoolId 클레임으로 학교별 데이터를 격리합니다. A학교 교사가 B학교 학생 데이터에 접근하면 403이 반환됩니다.

## 슬라이드 3: 아키텍처 (2분)

> 아키텍처를 설명드리겠습니다.
>
> 사용자는 CloudFront를 통해 React SPA에 접속하고, API 요청은 ALB를 거쳐 ECS Fargate 위의 Spring Boot로 라우팅됩니다.
>
> 데이터 계층은 의도적으로 **운영 DB와 분석 DB를 물리적으로 분리**했습니다. 왜냐하면 분석 쿼리의 GROUP BY + 다중 JOIN이 운영 트랜잭션과 자원을 경합하면, 교사가 성적을 입력하는 순간 응답이 느려지기 때문입니다.
>
> 두 DB 사이의 동기화는 **Kafka 이벤트 파이프라인**으로 처리합니다. 성적이 등록되면 Spring Event → Kafka Producer → Consumer → 분석 DB 집계 순서로 흐릅니다. 만약 분석 DB가 장애가 나도, Kafka에 이벤트가 쌓여 있다가 복구되면 자동으로 처리됩니다.
>
> 캐싱은 **Redis**를 JWT 블랙리스트 L1 캐시로 사용합니다. 매 API 요청마다 블랙리스트를 확인하는데, DB 조회 2~5ms를 Redis 1ms 미만으로 줄였습니다. Redis가 죽어도 DB fallback으로 서비스는 중단되지 않습니다.
>
> 모니터링은 **Prometheus + Grafana**를 ECS 사이드카로 배포했고, 앱 메트릭 10개, 비즈니스 메트릭 5개, CloudWatch 인프라 메트릭 4개로 **3계층 19개 패널**을 구성했습니다.

## 슬라이드 4: OLAP 파이프라인 + 멀티테넌시 (2분)

> OLAP 파이프라인을 좀 더 자세히 설명드리겠습니다.
>
> 교사가 성적을 등록하면, ScoreService에서 Spring ApplicationEvent를 발행합니다. AnalyticsEventBridge가 이 이벤트를 받아서 Kafka 토픽에 발행하고, ScoreAnalyticsConsumer가 소비해서 분석 DB의 student_score_summary, subject_statistics, student_learning_dashboard 테이블을 upsert합니다.
>
> 이 구조의 장점은 **장애 격리**입니다. 분석 DB가 죽어도 성적 입력은 정상 동작하고, Kafka에 이벤트가 쌓여있다가 backfill API로 복구할 수 있습니다.
>
> 멀티테넌시는 **Shared-Database, Discriminator-Column** 전략을 택했습니다. Database-per-tenant은 학교 수만큼 DB 인스턴스가 필요해서 비용이 비현실적이고, 우리 규모에서는 users 테이블의 school_id FK 하나로 충분합니다.
>
> 격리 방식은, 로그인 시 JWT에 schoolId를 넣고, JwtAuthenticationFilter에서 TenantContext라는 ThreadLocal에 저장합니다. 서비스 레이어에서는 메서드 시그니처 변경 없이 TenantContext.requireSchoolId()로 현재 학교를 확인하고, 다른 학교 데이터 접근 시 403을 반환합니다.

## 슬라이드 5: 성능 + 모니터링 (2분)

> 성능 측정은 k6로 200 동시 사용자 부하 테스트를 진행했습니다. 이는 10개 학교 교사가 동시에 시험 기간에 접속하는 시나리오입니다.
>
> Redis 도입 전 p95 응답시간이 906ms였고, 도입 후 791ms로 **13% 개선**되었습니다. 처리량은 133 req/s에서 140 req/s로 5% 향상됐고, 에러율은 0%입니다.
>
> 병목은 Analytics DB 쿼리 약 300ms로 확인했고, 이는 OLAP 분리가 필요한 이유이기도 합니다.
>
> 모니터링은 3계층으로 구성했습니다.
> - **앱 계층**: HTTP p95 응답시간, 5xx 에러율, JVM Heap, HikariCP 커넥션풀
> - **비즈니스 계층**: 성적/피드백/상담 등록 건수, 로그인 성공/실패율, Kafka Consumer Lag
> - **인프라 계층**: CloudWatch 연동으로 ECS CPU/Memory, RDS 커넥션, ALB 요청 수
>
> 왜 3계층인가? 사용자가 "성적 등록이 안 돼요"라고 신고하면, 비즈니스 메트릭에서 문제 존재를 확인하고, 앱 메트릭에서 5xx나 지연을 찾고, 인프라 메트릭에서 RDS CPU 100%가 원인임을 추적합니다. 위에서 아래로 **증상 → 원인** 순서입니다.
>
> 알림은 5개 규칙을 설정했고, 5xx 에러 발생 시 즉시 이메일 알림이 발송됩니다.

## 슬라이드 6: 라이브 데모 (2분)

> 실제 동작을 보여드리겠습니다.
>
> *(CloudFront URL 접속)*
>
> 교사 계정으로 로그인합니다. 좌측 사이드바에서 메뉴를 확인할 수 있습니다.
>
> 먼저 **성적 관리**입니다. 학생을 선택하면 우측 Drawer에서 검색할 수 있고, 선택 후 레이더 차트와 성적 테이블이 표시됩니다.
>
> **학생 분석 대시보드**로 가면, 이 학생의 6학기 성적 추이 차트, 위험도, 피드백/상담 통계를 한눈에 볼 수 있습니다.
>
> **AI 챗봇**입니다. 우하단 버블을 클릭합니다. "학생2의 성적 추이를 알려줘"라고 질문하면, AI가 실제 데이터를 조회해서 답합니다. "걔의 상담 내역은?"이라고 하면 이전 대화를 기억하고 같은 학생의 상담 데이터를 보여줍니다.
>
> 마지막으로 **멀티테넌시 격리**입니다. 한빛중학교 교사가 새별중학교 학생 데이터에 접근하면 403이 반환되어 교차 학교 접근이 완전히 차단됩니다.
>
> 감사합니다.
