## 🔴 반드시 나올 질문

### Q1. "왜 Kafka를 썼어요? 직접 DB에 넣으면 되잖아요."

> **나쁜 답변**: "Kafka가 좋은 기술이라서요" / "이벤트 기반이 트렌드라서요"
>
> **킬러 답변**:
> "분석 쿼리의 장애 격리 때문입니다. 분석 DB에 직접 insert하면, 분석 DB가 장애 나는 순간 성적 입력 API도 같이 죽습니다. Kafka를 중간에 두면, 분석 DB가 죽어도 이벤트가 Kafka에 쌓여있다가 복구 후 자동 처리됩니다. 실제로 backfill API로 수동 복구도 가능합니다.
>
> 그리고 Consumer를 독립적으로 스케일링할 수 있어서, 시험 기간에 10개 학교가 동시에 성적을 입력해도 Consumer 인스턴스를 늘려서 대응할 수 있습니다."

---

### Q2. "운영 DB와 분석 DB를 왜 분리했어요?"

> **킬러 답변**:
> "분석 쿼리가 운영 트랜잭션과 자원을 경합하기 때문입니다. 예를 들어, 과목별 통계를 계산하는 GROUP BY + 다중 JOIN 쿼리가 실행되는 동안, 교사가 성적을 입력하면 응답시간이 급격히 느려집니다.
>
> 실제 부하 테스트에서 병목이 Analytics DB 쿼리 약 300ms로 확인됐는데, 이게 운영 DB에서 돌아가고 있었다면 성적 입력 p95가 1초를 넘겼을 겁니다.
>
> 물리적으로 분리하면 분석 쿼리가 아무리 무거워도 성적 입력에는 영향이 없습니다."

---

### Q3. "Redis를 왜 썼어요? 효과가 고작 13%인데 도입할 가치가 있나요?"

> **킬러 답변**:
> "현재 200명 동시 접속에서는 13%지만, Redis를 도입한 진짜 이유는 **동시 1000명 이상에서 커넥션 풀 고갈 방지**입니다. 매 API 요청마다 JWT 블랙리스트를 DB에서 확인하면, 200 스레드 × DB 커넥션 = HikariCP max 20이 즉시 고갈됩니다.
>
> Redis는 커넥션 풀을 소비하지 않으므로 동시 접속이 늘어도 DB 부하가 증가하지 않습니다. 그리고 Redis가 죽어도 DB fallback으로 서비스는 중단되지 않도록 설계했습니다.
>
> 실측 수치로는, DB 조회 2~5ms가 Redis 1ms 미만으로 줄었고, 부하 테스트에서 HikariCP pending이 0으로 유지됐습니다."

---

### Q4. "다중 학교를 어떻게 격리하나요?"

> **킬러 답변**:
> "Shared-Database, Discriminator-Column 전략입니다. users와 classes 테이블에 school_id FK를 추가하고, 나머지 테이블은 FK 체인으로 학교를 추론합니다.
>
> 로그인하면 JWT에 schoolId 클레임이 포함되고, JwtAuthenticationFilter에서 TenantContext라는 ThreadLocal에 저장합니다. 서비스 메서드 시그니처를 변경하지 않고도 모든 레이어에서 현재 학교를 알 수 있습니다.
>
> 한빛중학교 교사가 새별중학교 학생에 접근하면 403이 반환됩니다. 실제로 테스트 완료했습니다.
>
> Database-per-tenant을 선택하지 않은 이유는, 학교 수만큼 DB 인스턴스가 필요해서 10개 학교면 RDS 비용이 10배입니다. Discriminator Column이면 하나의 DB로 충분합니다."

### Q5. "AI 챗봇은 어떻게 구현했어요? 왜 Function Calling만 안 쓰고 RAG도 넣었어요?"

> **킬러 답변**:
> "처음에는 Function Calling만으로 정형 데이터를 조회했습니다. 하지만 교사 업무에서는 피드백·상담 같은 비정형 텍스트가 중요합니다. '수업 태도 문제 있는 학생 찾아줘'는 SQL로 안 됩니다 — '수업 태도 문제'라는 표현이 정확히 같은 단어로 저장되어 있지 않을 수 있기 때문입니다.
>
> 그래서 **Hybrid Architecture**로 고도화했습니다:
> - **정형 데이터** → Function Calling (16개 Tool)
> - **비정형 텍스트** → RAG + pgvector 의미 검색
> - **보고서 생성** → Function Calling + RAG + LLM 하이브리드
> - **위험 감지** → Kafka Consumer Proactive 알림
>
> pgvector를 선택한 이유는 기존 PostgreSQL에 확장만 추가하면 되어 인프라 비용이 $0입니다. Chroma나 Pinecone은 별도 인프라가 필요합니다.
>
> JDBC 바인딩은 벡터를 문자열로 변환 후 `?::vector` SQL 캐스팅으로 안전하게 바인딩합니다. HikariCP + PostgreSQL JDBC 42.7 환경에서 호환성 문제가 있어 이 방식을 선택했고, PreparedStatement 파라미터 바인딩이므로 SQL injection 위험이 없습니다.
>
> RAG 검색은 단순 벡터 유사도가 아니라 **school_id, 학년도, 역할 범위로 메타데이터 필터링**을 먼저 적용합니다. AI가 전체 데이터를 자유롭게 검색하는 것이 아니라, 현재 사용자가 접근 가능한 범위 안에서만 검색합니다. 실제로 544건의 피드백과 271건의 상담이 임베딩되어 있고, 유사도 0.7 이상의 결과를 반환합니다.
>
> 학기말 종합 의견 생성은 Function Calling으로 성적을 수집하고, RAG로 피드백·상담 텍스트를 찾고, LLM이 초안을 생성합니다. 프론트엔드에서는 보고서 카드로 초안 본문, 참고 근거(피드백/상담 출처), 교사 수정 UI를 제공합니다. 교사가 근거를 확인하고 수정한 뒤 저장하면 수정 거리(edit_distance)가 기록되어 AI 품질을 추적합니다. 이것은 Fine-tuning이 아니라 프롬프트 개선입니다.
>
> 모든 AI 요청은 감사 로그에 기록됩니다."

### Q6. "모니터링을 왜 3계층으로 나눴어요?"

> **킬러 답변**:
> "한 계층만 보면 **원인을 못 찾기** 때문입니다.
>
> 예를 들어, 교사가 '성적 등록이 안 돼요'라고 신고하면:
> 1. 비즈니스 메트릭에서 성적 등록 0건을 확인 → 문제 존재 확인
> 2. 앱 메트릭에서 HTTP 5xx 급증 확인 → 서버 에러
> 3. 인프라 메트릭에서 RDS CPU 95% 확인 → 원인: DB 병목
>
> 위에서 아래로 **증상 → 원인** 순서로 추적합니다. 비즈니스 메트릭 없이 인프라만 보면 CPU가 정상이어도 사용자는 장애를 겪을 수 있습니다."

## 🟡 자주 나올 수 있는 질문

### Q7. "ECS Fargate를 선택한 이유는?"

> "EC2 대비 인프라 관리가 불필요하고, Kubernetes 대비 학습 곡선이 낮습니다. 서버 패치, OS 업데이트를 AWS가 담당하므로 우리는 컨테이너 이미지와 배포에만 집중할 수 있습니다.
>
> 비용은 0.5 vCPU + 1GB 기준 시간당 약 $0.034로, EC2 t3.micro($0.013)보다 비싸지만, 운영 부담을 고려하면 합리적입니다. Auto Scaling도 ECS 서비스 레벨에서 설정하면 됩니다."

### Q8. "CloudFront를 왜 썼어요?"

> "프론트엔드는 정적 파일(React SPA)이라 CDN 캐싱이 가장 효과적입니다. 서울 리전 ALB에서 직접 서빙하면 다른 지역 사용자에게 지연이 생기지만, CloudFront는 전국 엣지 로케이션에서 서빙합니다. API 요청은 CloudFront → ALB → ECS로 프록시합니다."

### Q9. "테스트 커버리지는 얼마예요?"

> "SonarCloud 기준 83.6%입니다. 엔티티, DTO, Config 클래스는 JaCoCo 제외 설정을 했고, 핵심 서비스 로직에 집중해서 테스트했습니다. 단위 테스트, 컨트롤러 테스트, 통합 테스트를 포함해서 약 400개 이상의 테스트가 있습니다."

### Q10. "보안은 어떻게 처리했어요?"

> "4가지 레이어입니다.
> 1. **접근 제어**: 자유 회원가입 없음. Admin이 사전 등록한 전화번호 + SMS OTP로만 계정 활성화.
> 2. **인증**: JWT Access Token(30분) + Refresh Token Rotation(7일). 블랙리스트로 로그아웃 처리.
> 3. **인가**: 역할 기반(RBAC) + 학교 기반(TenantContext). 교사도 자기 학교 데이터만.
> 4. **데이터 암호화**: 상담 내용, 이메일, 전화번호는 AES-256-GCM으로 암호화."

### Q11. "확장성은 어떻게 확보했어요?"

> "현재 MVP는 2개 학교지만, 성장 경로를 고려해서 설계했습니다.
> - Phase 1 (10개 학교): 커넥션 풀 20→100, ECS 태스크 1→3
> - Phase 2 (100개 학교): RDS Read Replica, Kafka 파티션 증가, Redis Cluster
> - Phase 3 (1000+): Database-per-tenant 전환 검토
>
> 인프라를 다시 설계할 필요 없이 **설정 변경과 리소스 증가**만으로 대응 가능합니다."

## 🟢 까다로운 질문 (차별화 포인트)

### Q12. "scores 테이블에는 school_id를 안 넣었는데, 왜?"

> "정규화 원칙입니다. scores → student → user → school FK 체인으로 학교를 추론할 수 있습니다. 역정규화는 성능 병목이 실측될 때 하는 것이지, 미리 하는 것이 아닙니다. 현재 FK 체인 조인으로 성능 문제가 없으므로 추가하지 않았습니다."

### Q13. "TenantContext를 ThreadLocal로 했는데, 비동기에서는?"

> "좋은 질문입니다. @Async 이벤트에서는 ThreadLocal이 전파되지 않으므로, 이벤트 페이로드에 schoolId를 직접 포함시켰습니다. Kafka Consumer도 페이로드에서 schoolId를 추출해서 Analytics DB에 저장합니다."

### Q14. "부하 테스트 200명은 적은 거 아닌가요?"

> "200 VU는 10개 학교 교사가 동시에 시험 기간에 접속하는 시나리오입니다. 학교당 교사 20명 × 10개 학교 = 200명. 현재 인프라(ECS 0.5 vCPU, RDS db.t3.micro)에서 p95 791ms, 에러율 0%를 달성했습니다. 인프라 스펙을 올리면 1000+ VU도 가능합니다."

### Q15. "이 프로젝트에서 가장 어려웠던 점은?"

> "멀티테넌시 리팩토링입니다. 이미 완성된 코드에 school_id를 추가하는 거라, 모든 서비스와 레포지토리, 테스트를 수정해야 했습니다. 특히 JPA Lazy Loading과 TenantContext의 트랜잭션 범위 문제가 까다로웠는데, AnalyticsAccessChecker에 @Transactional을 추가하고, 조회 메서드마다 학교 검증을 넣어서 해결했습니다.
>
> 이 경험에서 배운 건, 멀티테넌시는 처음부터 설계에 포함해야 한다는 것입니다. 나중에 추가하면 작업량이 5배 이상 늘어납니다."
