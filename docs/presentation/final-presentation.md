## 슬라이드 1: 문제 정의 + 소개 (1분)

**슬라이드 내용**: 프로젝트명, 기술 스택, 문제 상황 3줄

**대본**:

> 안녕하세요, 이승희입니다.
>
> SSCM, Smart School Class Management를 개발했습니다.
>
> 현재 학교 현장에서 교사가 학생 한 명을 파악하려면 **성적은 나이스, 피드백은 엑셀, 상담 기록은 한글 파일, 학생부는 또 다른 시스템**에서 따로 봐야 합니다. 학기말에 종합 의견을 쓰려면 이 자료들을 직접 모아서 정리해야 하고, 30명 분을 하려면 며칠이 걸립니다.
>
> SSCM은 이 문제를 해결합니다. 모든 교육 데이터를 하나로 통합하고, 실시간 분석 대시보드와 AI 어시스턴트로 교사의 데이터 기반 의사결정과 기록 업무를 돕습니다.
>
> Spring Boot 3.5, React 19, PostgreSQL 16 기반이고 AWS에 프로덕션 배포되어 있습니다.

## 슬라이드 2: 핵심 기능 4가지 (1분 30초)

**슬라이드 내용**: 4개 기능 블록 다이어그램 (아이콘 + 한 줄 설명)

**대본**:

> 핵심 기능은 4가지입니다.
>
> **첫째, 교육 데이터 통합 관리.**
> 성적, 학생부, 피드백, 상담을 하나의 시스템에서 CRUD합니다. 역할별 접근 제어가 있어서 교사, 학생, 학부모가 각각 볼 수 있는 데이터가 다릅니다.
>
> **둘째, OLAP 분석 파이프라인.**
> 운영 DB와 분석 DB를 물리적으로 분리했습니다. Kafka로 이벤트를 동기화하기 때문에 분석 쿼리가 아무리 무거워도 성적 입력에 영향을 주지 않습니다.
>
> **셋째, Hybrid AI 교육 어시스턴트.**
> 단순 조회 챗봇이 아닙니다. 정형 데이터는 Function Calling 16개 도구로 조회하고, 비정형 텍스트는 RAG + pgvector로 의미 검색합니다. "수업 태도 문제 있는 학생 찾아줘"라고 하면 544건의 피드백에서 의미가 유사한 기록을 찾습니다.
>
> 학기말 종합 의견은 성적 + 피드백 + 상담을 조합해서 AI가 초안을 생성하고, 교사가 근거를 확인하고 수정하는 Human-in-the-Loop 구조입니다. 또한 Kafka Consumer가 성적 급락을 감지하면 교사에게 먼저 알림을 보냅니다.
>
> **넷째, 다중 학교 멀티테넌시.**
> JWT에 schoolId를 넣고, TenantContext로 학교별 데이터를 격리합니다. A학교 교사가 B학교 학생 데이터에 접근하면 403이 반환됩니다.

## 슬라이드 3: 아키텍처 (1분 30초)

**슬라이드 내용**: 시스템 아키텍처 다이어그램 (CloudFront → ALB → ECS → RDS×2 + Redis + Kafka)

**대본**:

> 아키텍처입니다.
>
> 사용자는 **CloudFront CDN**을 통해 React SPA에 접속하고, API 요청은 ALB를 거쳐 **ECS Fargate** 위의 Spring Boot로 라우팅됩니다.
>
> 데이터 계층은 **운영 DB와 분석 DB를 물리적으로 분리**했습니다. 왜냐하면 분석 쿼리의 GROUP BY + JOIN이 운영 트랜잭션과 자원을 경합하면 성적 입력이 느려지기 때문입니다. 두 DB 사이의 동기화는 **Kafka**가 담당합니다.
>
> **Redis**는 JWT 블랙리스트 캐시입니다. 매 API 요청마다 블랙리스트를 DB에서 확인하면 커넥션 풀이 고갈되는데, Redis로 1ms 미만으로 줄였습니다. Redis가 죽어도 DB fallback으로 서비스는 중단되지 않습니다.
>
> AI 기능은 운영 DB에 **pgvector 확장**을 추가해서 벡터 검색을 수행합니다. 별도 벡터 DB 없이 기존 PostgreSQL에서 처리하므로 인프라 비용이 추가되지 않습니다.
>
> 모니터링은 **Prometheus + Grafana**를 ECS 사이드카로 배포했고, 3계층 19개 패널과 5개 알림 규칙을 구성했습니다.

## 슬라이드 4~8: 라이브 데모 (3분 30초)

**슬라이드**: 브라우저 화면 전환 (프로젝터에 CloudFront URL 또는 localhost 접속)

### 데모 1: 로그인 + 핵심 기능 (40초)

> "교사 계정으로 로그인합니다."

- `teacher@sscm.dev` / `teacher1234`
- 대시보드: 인사말 + 통계 카드 + AI 위험 알림 섹션
- 성적 관리: 학생2 선택 → 우측 Drawer → 레이더 차트 + 성적 테이블

> "학생을 선택하면 6학기 성적과 레이더 차트가 바로 표시됩니다."

### 데모 2: 분석 대시보드 (30초)

- 사이드바 → 학생 분석 → 학생2 선택
- 요약 탭: KPI 카드 (평균 68점, 위험도 MEDIUM, 추이 DOWN)
- 성적 탭: 6학기 추이 차트 (89점 → 61점 하락)

> "이 학생은 2024년 B+에서 2026년 D까지 지속 하락하고 있습니다."

### 데모 3: AI 챗봇 — Function Calling (40초)

- 우하단 챗봇 버블 클릭
- 입력: **"학생2 성적 추이 알려줘"**
- AI가 이름 검색 → 학생2(ID:3) 매핑 → 6학기 추이 응답

> "학생 이름으로 질문하면 AI가 자동으로 학생을 검색하고 실제 데이터를 조회합니다."

- 입력: **"걔 상담 내역은?"**
- AI가 대화 맥락 유지 → 같은 학생의 상담 데이터 반환

> "이전 대화를 기억하기 때문에 '걔'라고만 해도 같은 학생 데이터를 봅니다."

### 데모 4: AI 챗봇 — RAG 의미 검색 (30초)

- 입력: **"2026년 1학기 수업 태도 문제 있는 학생 찾아줘"**
- AI가 pgvector로 544건 피드백에서 의미 검색 → 유사도 0.76으로 관련 학생 반환

> "SQL LIKE 검색이 아닙니다. '수업 태도 문제'라는 의미를 벡터로 변환해서 유사한 피드백을 찾습니다. 유사도 점수와 함께 표시됩니다."

### 데모 5: AI 챗봇 — 종합 의견 생성 + HITL (50초) ★

- 입력: **"학생2 종합 의견 작성해줘"**
- AI 응답 + **파란 보고서 카드** 표시

> "AI가 성적, 피드백, 상담을 종합해서 초안을 생성했습니다."

- **"참고 근거 (5건)"** 클릭하여 펼치기
  - [피드백] 과제 제출이 꾸준하고 성실합니다
  - [상담] 기말고사 대비 학습 전략 상담
  
> "참고 근거를 펼쳐보면 어떤 피드백과 상담이 근거로 사용되었는지 확인할 수 있습니다."

- **"수정하기"** 클릭 → 텍스트 일부 수정 → **"교사 수정본 저장"** 클릭
- "수정본이 저장되었습니다" 메시지

> "교사가 검토 후 수정하면 Human-in-the-Loop으로 저장됩니다. 수정 거리를 기록해서 AI 품질을 추적합니다."

### 데모 6: 멀티테넌시 (20초)

> "마지막으로 다중 학교 격리입니다."

- 터미널에서 curl 실행 (미리 준비):
  ```
  한빛중 교사 토큰으로 새별중 학생 데이터 접근 → 403 Forbidden
  ```

> "한빛중학교 교사가 새별중학교 학생 데이터에 접근하면 403이 반환됩니다."

## 슬라이드 9: 성능 + 모니터링 (1분 30초)

**슬라이드 내용**: 부하 테스트 수치 표 + 3계층 모니터링 구조도

**대본**:

> 성능입니다. k6로 200 동시 사용자 부하 테스트를 했습니다. 10개 학교 교사가 시험 기간에 동시 접속하는 시나리오입니다.
>
> Redis 도입 전 p95 906ms, 도입 후 **p95 791ms로 13% 개선**, 처리량 140 req/s, 에러율 0%입니다.
>
> 13%가 적어 보일 수 있지만, Redis의 진짜 가치는 **동시 1000명 이상에서 DB 커넥션 풀 고갈 방지**입니다. 매 요청마다 블랙리스트를 DB에서 확인하면 HikariCP max 20이 즉시 고갈됩니다.
>
> 모니터링은 **3계층**입니다.
> - **비즈니스**: 성적 등록 건수, AI 챗봇 사용량
> - **앱**: HTTP p95, 5xx 에러, JVM Heap
> - **인프라**: ECS CPU, RDS 커넥션
>
> 왜 3계층인가? "성적 등록이 안 돼요"라고 신고가 오면 — 비즈니스에서 문제 확인, 앱에서 5xx 확인, 인프라에서 RDS CPU 95%가 원인. **증상에서 원인으로** 추적합니다.
